Detailed Description

Base class for a pluggable strategy that arranges a Container's current children within it (see Container::set_layout()). A Container with no layout attached (the default) leaves its children exactly wherever they've been explicitly positioned/sized, entirely unmanaged; attaching one of these takes over that job instead, kept in sync automatically as the container's children or own size change (see Container::add_child(), remove_child(), or set_size()).

Every concrete layout also offers its own add_child() (and, where its own strategy actually has a notion of "where", e.g.,BoxLayout::insert_child(), further placement methods besides), each with whatever parameters that strategy actually needs to place a new child; adding one through Container::add_child() directly instead bypasses that, leaving it unarranged by this layout.

Returns this layout's own container, set once by Container::set_layout() right after construction: the one a concrete layout's own add_child() (see, e.g., BoxLayout::add_child()) actually adds a new child through. Read-only from here on purpose: only Container::set_layout() itself ever gets to set this, not a subclass.

◆ calculate_minimum_size()

virtual ml7::Vector2f fl7::gui::layout::Layout::calculate_minimum_size ( const Container & container) const
inlinevirtual

Returns how large this layout's own strategy would ideally like container to be, given its current children's own effective minimum sizes, while this layout is attached, instead of the plain (no-layout) bounding-box calculation a Container otherwise falls back to. Default: {0, 0} (no particular opinion; a layout that doesn't actually resize/reposition children, e.g., DefaultLayout, has none to report either).
